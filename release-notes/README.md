# 发布说明规范

GitHub Release 面向用户的完整说明以 `release-notes/<版本>.md` 为唯一正文来源，正式版、补丁版和预发布都适用。CHANGELOG 继续记录开发变化，不直接拼接提交标题或复制全部开发记录作为发行说明。新版本发布前必须有对应文件；历史版本在普通检查中仍兼容 CHANGELOG，不要求补写旧说明。

## 固定结构与写法

从 [模板](TEMPLATE.md) 创建版本文件，使用 `# JHS <版本>` 标题，并在摘要中明确比较版本。二级分类依次为 **新增、修复、改进、升级说明、致谢**，没有内容的分类直接省略，不写“无”。重要功能可用三级标题展开。

- 新增只写此前没有的用户能力。已发布功能、代码搬迁和旧功能重新实现归入改进。
- 修复写清触发场景、原有问题及修复后的行为，附有依据的 PR 或 Issue 链接。
- 先写用户能感知的变化，再补必要的技术原因；不把 CI、测试环境、开发产物或发布脚本调试当作产品更新。
- 升级说明只保留必要的安装、配置、兼容与切换事项。不写未经验证的性能提升、稳定性保证或贡献归属。
- 致谢区分代码贡献与问题反馈，只列本版本实际采纳的内容。手动适配注明适配，不声称直接合并；历史贡献不重复计入，维护者不自我致谢。

## 范围与贡献核对

| 发布类型 | 默认比较基点 |
| --- | --- |
| 新版本首个 RC | 上一个正式版本 |
| 后续 RC | 同系列上一个 RC |
| 正式大版本 | 上一个正式版本，累计包含 RC 阶段变化 |
| 正式补丁版 | 上一个正式版本 |

必须记录基点和目标的完整提交 SHA，并检查祖先关系；不能按日期、最近几个提交或作者数量推断范围。编写前查看实际代码差异、完整提交正文、关联 PR 和 Issue。关闭未合并的 PR 可能已手动适配，也可能未采纳，须结合提交说明和代码核对。

只读命令需要本地 Git 历史及已授权的 GitHub CLI 读取能力，不抓取、修改 Git 引用或写入线上内容：

```powershell
npm run release:notes:context -- --target v7.0.0-rc.1 --version 7.0.0-rc.1
npm run release:notes:context -- --base v6.5.2 --target v7.0.0-rc.1 --version 7.0.0-rc.1 --adopted-pr 13:f280976
npm run check:release:notes
npm run check:release:notes -- 7.0.0-rc.1
```

未指定基点时只从目标的祖先标签中选择。核对报告写入忽略的 `output/release-notes-context/`，包含完整提交、模块路径变化、PR/Issue、作者和候选贡献者。`--adopted-pr` 是完成代码审阅后的人工确认，必须给出范围内且明确引用该 PR 的提交；引用本身不等于采纳。报告保留待核对状态，不自动生成最终致谢。

Windows PowerShell 如由 `npm.ps1` 截获 `--version` 等参数，将上述命令的 `npm` 改为 `npm.cmd`，参数含义不变。

RC1 的范围是 `v6.5.2` → `v7.0.0-rc.1`：PR #13 的方案在 `f280976` 适配，Issue #15 对应 `fc6f881` 的 115 修复。本版感谢 @SeraphHsing 与 @elysioneo；#1、#4、#12 等历史贡献属于基点或更早版本，不重复计入。

## 发布与正文修订

`npm run check` 检查现有版本说明；新正式版在发布契约检测到升版时强制读取版本文件，RC 在构建和发布前读取同一文件。历史 CHANGELOG 解析、稳定版版本校验及返回接口继续保留。普通文档提交不自动修改线上 Release。

已发布版本只改正文时，先提交审核后的版本文件和工具到 develop，再显式推送 `notes-v<版本>-r<N>` 标签，例如 `notes-v7.0.0-rc.1-r1`。每次修订递增编号，不覆盖既有修订标签。工作流从标签提交读取规范及正文，支持尚未进入默认分支的实现，拒绝被更高修订取代的旧任务。

正文修订入口先确认目标 Release 已发布，API 请求只包含 `body`。更新后逐字回读，并核对 Release ID、版本标签、名称、目标、发布类型、发布时间、附件 ID/大小/摘要、原标签及稳定版 Latest 不变。它不创建 Release、不上传附件、不更新 RC 通道、不移动版本标签。发生 API 或核验失败时任务失败，排查后以明确的修订重试，不自动回退正文。

共用支持在 develop 落地，main 随正常合入启用；不为正文修订单独推送 main。

## 7.0 RC 候选与发布

RC 独立名称为 `JHS RC 7.0`，版本从 `7.0.0-rc.1` 开始；namespace 固定为 `https://github.com/Teamper/JHS/rc/7.0`。RC 只跟随本系列更新，7.0 正式版需要手动切换。稳定版元数据仍为 6.5.2，存储和公共接口不变。

## 候选清单

候选包含 develop 的 7.0 重构、115 完整番号匹配、完整设置草稿和统一保存、Fluent 分组列表与滚动条，以及已完成的列表、手机、键盘和异步生命周期修复。纳入对应源码、契约测试、浏览器测试及实际审阅的视觉基线。构建及审计脚本的现有改动须一并审查，资源编码继续关闭。

排除根目录本地 Dev 交付副本、output 样稿和测试产物、AGENTS.md、计划、提示词及个人过程文件。冻结前以实际 diff 逐项记录路径及理由，不能用全目录暂存替代审查。当前工作区的未提交内容保留原地；整理提交、推送、创建标签与公开发布分别需要明确指令。

## 本地冻结与验收

在已审查且干净的源码提交上运行：

```powershell
npm run build:rc -- 7.0.0-rc.1
npm run check:rc:delivery -- dist/rc/7.0.0-rc.1/JHS-7.0.rc.user.js
npm run check:rc -- 7.0.0-rc.1
```

构建拒绝跟踪或未跟踪文件改动。产物位于 dist/rc/版本目录，包含用户脚本、元数据、SHA256SUMS 和 release-manifest.json。同一版本现有文件只有完全一致才可复用。check:rc 冻结文件后运行完整检查、功能检查及视觉门禁，报告在 output/rc-validation。启动耗时与串行性能保留原阈值和检查，结果只作参考报告，不阻断 RC 发布，不要求配置本机 runner。默认 Dev 测试身份不变；RC 使用显式 JHS_TEST_CHANNEL=rc 与 JHS_TEST_BUNDLE_PATH。不得改阈值或以 Dev 报告替代 RC 验收。

还需在隔离 Tampermonkey 配置中，用受控更新地址实际验证 rc.1 → rc.2 → rc.10、独立安装身份、更新失败保留原安装和 RC 内凭证保留。正式元数据必须恢复固定公开通道。此人工验收应记录浏览器/扩展版本、步骤与结果，作为标签发布前的人工检查；CI 不声称覆盖扩展安装验收。

## 发布与恢复

明确授权并完成候选及人工验收后，推送唯一的 v7.0.0-rc.N 标签。独立 RC 工作流校验标签指向 develop 提交，依次运行构建、功能和视觉等硬检查，记录启动耗时与串行性能参考结果，发布 prerelease 且 make_latest=false，下载附件核验后在 rc-channel 分支一次提交更新脚本、元数据和清单。main 稳定版工作流不变。每个版本需有 release-notes/版本.md 发布说明。

固定通道为 https://raw.githubusercontent.com/Teamper/JHS/rc-channel/ 下的 JHS-7.0.rc.meta.js 与 JHS-7.0.rc.user.js。GitHub latest 不用于 RC。不同文件的 CDN 缓存可能有延迟，公开端点不一致时工作流失败并保留诊断，稍后重跑同一版本核验。若分支提交已经完成，不声称失败会自动撤回通道。

重跑只复用同一源码与相同字节，不覆盖发布附件；非快进通道推送直接失败。更高 RC 标签存在后，旧标签不得再次晋升通道。修复已发布缺陷必须使用更高编号，不倒退版本、不自动恢复数据库。最后一个 RC 通道保留，正式版手动切换。

## 仅重试发布

当候选与 Node 20 作业已通过、仅发布失败时，可用 release-rc-retry 工作流复用原候选。恢复入口显式固定版本与验证运行 ID，必须核对原运行属于本仓库 RC 标签流程、已完成且两个必要作业成功；原标签、源码 SHA、四份交付文件和重新构建结果均须一致。恢复标签采用 rc-publish-retry-版本-原运行ID，指向发布工具修复提交，不移动原 RC 标签、不更换验收产物。注释标签和轻量标签均按远端剥离后的提交核验，不通过强制覆盖本地标签解决检出差异。
